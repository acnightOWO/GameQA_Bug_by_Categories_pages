Game QA 研究報告 · 2026 年 11 月

遊戲 Bug 地圖

遊戲測試想自動化，先要知道「要抓什麼」。這份報告的順序是：為什麼要自動化 → 為什麼要先替 bug 分類 → 每一類做到哪裡、卡在哪裡 → 接下來可以做什麼。

目錄：
  1. 為什麼要自動化遊戲 QA
  2. 為什麼要先分類，以及怎麼分
  3. 每一類做到哪裡
  4. 各類共同的缺口
  5. 可以前進的方向

一、為什麼要自動化遊戲 QA

現在遊戲測試幾乎全靠人工試玩，而且人工有兩個加人也解決不了的問題：

  • Politowski 等人 2021（arXiv；想整理遊戲測試研究的全貌；做法是文獻回顧）：結論是業界「幾乎完全依賴人工試玩和測試者的經驗」。
  • 組合太多：Truelove 問卷裡的開發者說，每種動作在每種情境下的每種順序，「組合上通常不可能測完」。
  • 量太大：測試公司 TestBird 2020 年測了 11,476 款手機遊戲，回報 552,851 個相容性問題；同一款還要在不同裝置、解析度、語系上各看一遍。

自動化能補這個缺口，但業界還沒用起來：

  • Bergdahl 等人（EA，2020）（想用強化學習補強自動測試；在自製關卡訓練 agent，跟照路線走的腳本 agent 比）：估計平行跑的 agent 每秒約 3 萬個動作，等於 3,000 名玩家。
  • Politowski 等人 2022（arXiv；想知道學術方案離業界需求多遠；文獻回顧加開發者問卷，12 人）：開發者對自動化 agent 存疑，最大的顧慮是前期成本，論文裡的方案沒有一個適合小團隊。
  • Zhang 等人（2025，2026 年修訂；想知道 AI 輔助能不能讓人工測試更準；用 GPT-4o 標出可疑的地方給測試者看，276 位受試者、800 個測試案例）：有 AI 輔助時找出缺陷的正確率 62.7%，純人工 41.3%；但 AI 判錯時也會把人帶錯。
  • 技術上卡兩件事：程式怎麼走到 bug，以及走到後怎麼認出它是錯的（oracle）。

二、為什麼要先分類，以及怎麼分

不同的 bug，需要的資訊完全不同

「走到」和「認出」有多難，每種 bug 差很多：

bug 的種類走到它認出它需要的資訊
當機難：要重現路徑不需要，程式關掉就是錯
畫面渲染中等一張截圖
時間性 glitch中等一段影片
動作與互動難：操作組合爆炸影片加上玩家輸入，有時還要遊戲內部狀態
資訊與介面中等文字被畫壞：截圖；內容寫錯：正確答案（內部數值、資料檔）

本報告依各類文獻的整理，不是單一論文的原表。

所以沒有一種方法能通吃。先分類，才能：

  • 依頻率和嚴重度決定先做哪一類；
  • 知道每一類要餵給程式什麼資訊；
  • 用同一把尺比較各類的研究進度。

現有的分類

主流分類都看玩家看到什麼，不看程式哪裡寫錯。主要有三套，一套接一套：

  • Lewis 等人（2010）（想回答「遊戲會怎麼壞」；蒐集線上影片、文章和玩家社群裡的 glitch 來分類）：11 類，最上層分「要看前後變化才知道錯」和「一張畫面就看得出來」。
  • Truelove 等人（2021）（想知道哪些 bug 最常被修、最常復發、最嚴重；拿 Lewis 的分類一行行標 Steam 更新說明，再問卷 47 位開發者）：標了 30 款熱門遊戲、723 次更新裡的 12,122 筆修正，補 9 類，共 20 類。唯一有大規模頻率資料，本報告以它為骨架。
  • Butt 等人（2023）／VGBT（2025）（想做一套更完整的分類；多來源文獻回顧加從業者問卷）：擴充到 63 類；期刊版 VGBT 套用到 0 A.D. 的 594 份回報，但只有這一款遊戲。

本報告看的五類

依頻率、嚴重度和「認出它要什麼資訊」，把 20 類收成五個主題：

主題對應 Truelove 類別為什麼選
當機Crash最嚴重、最常復發
畫面渲染Game Graphics，以及看得見的 Collision、Position of Object第二常見、第二常復發
時間性 glitchLewis「跟時間有關」中，跟動作與畫面變化有關的部分Lewis 分類最上層的一半；近兩年研究集中，模型成績最差
動作與互動Action、Triggered Event、Context State、Object PersistenceAction 第三常見；Triggered Event 常復發、嚴重
資訊與介面Information、User Interface最常見

不涵蓋：音效、網路與效能（Implementation Response；卡頓除外，它的偵測方式跟時間性 glitch 相同）、作弊漏洞、NPC 行為、鏡頭、數值設定（Value）、物件屬性交互、出界（Bounds）。研究方向與這五類差異大，另行處理。

當機：不難認出，難在重現

  • 開發中：讓 agent 自己玩到當掉
    • Wuji（網易，ASE 2019；想自動測戰鬥遊戲；演化演算法加強化學習，讓 agent 一邊打贏一邊往沒去過的地方走）：在兩款商業遊戲找到 3 個新 bug。
    • TITAN（預印本；想讓 LLM agent 取代 RL 來玩和測；GPT-4o 玩兩款 MMORPG，再用當機、卡關、超時三種自動判定整理報告）：注入 bug 偵測率 82%，Wuji 45.5%。
  • 收到回報後：照玩家的描述重新走到當機
    • AdbGPT（ICSE 2024；想自動重現 Android app 的 bug 回報；LLM 把回報拆成步驟，再在畫面上依序執行）：自報 81.3%，別人重測只有 74% 和 36%。
    • BugCraft（ASE 2025；想把同樣的事搬到遊戲；LLM 整理步驟，再由看得懂畫面的 agent 用 Minecraft 專用指令執行）：86 份 Minecraft 當機回報最好重現 34.9%，LLM 寫出的步驟三分之一是錯的。
  • 上線後：決定先修哪個
    • Weeraddana 等人（Ubisoft，ICSE SEIP 2025；想提早找出會快速擴散的當機；用前一款遊戲的資料預測新遊戲）：比對 stack trace 勝過機器學習，找出超過一半的這類當機。
  • 缺口：遊戲版只有 Minecraft 一個 benchmark；每款遊戲都要重寫一套操作指令。

畫面渲染：研究最多，但多在公開資料上

  • 造壞畫面來訓練
    • GLIB（網易，FSE 2021；想自動判斷截圖有沒有畫面 glitch；改遊戲的渲染程式產生大量壞畫面，訓練 CNN）：recall 從只用真實截圖的 0.563 升到 0.990；但每款遊戲都要原始碼。
  • 只學正常畫面
    • World of Bugs（Wilkins & Stathis 2022；想不靠壞畫面樣本也能抓 bug；只用正常畫面訓練模型，還原不回來的就算異常）：黑畫面、貼圖遺失幾乎全抓到，穿模幾乎抓不到。
  • 直接問 VLM
    • VideoGameQA-Bench（NeurIPS 2025；想量 VLM 能不能做遊戲 QA；用 Steam 截圖和影片出多種題型）：GPT-4o 在圖片 glitch 題 82.8%。
    • Lu 等人，找 bug 畫面（與 EA 合作；想從 bug 回報的影片找出出事的那一格；讓 GPT-4o 依文字描述挑關鍵幀）：論文討論段改用 VideoGameQA-Bench 的提示測 100 張 EA 開發截圖，只有 46%。
    • Lu 等人，41 小時錄影（與 EA 合作；想知道 VLM 在真實測試錄影上能做到多少；把錄影抽成約兩萬張關鍵幀交給模型，再試加裁判模型和檢索）：gpt-4.1-mini 報出來的約一半是誤報。
  • 給參考畫面
    • RefGlitch-Bench（預印本；想知道給一張正常的參考圖能不能幫 VLM；在 Godot 場景做 1,000 組參考與測試配對）：對多數模型有幫助，但自動選的參考本身也可能是壞的。
  • 缺口：公開資料偏向明顯的 glitch。Sony 的穿模研究（IEEE CoG 2026；想量 VLM 抓穿模的能力；讓 agent 探索 Godot 場景，改引擎自動標出穿模）發現，正常畫面換成靠牆、被遮住這類模稜兩可的，誤報大增。

時間性 glitch：模型幾乎在猜

  • 什麼樣的 bug：角色滑行沒邁步、物件忽隱忽現，暫停在任何一格都看不出來。
  • TempGlitch（Alberta 與 Sony，預印本；想量 VLM 能不能抓時間性 glitch；在 Godot 範例裡注入 glitch，每支再配一支刻意做得很像的正常影片）：12 個模型都在 49%–54%，等於亂猜；多給畫面也沒用。
  • Huynh & Pham（Zenodo 預印本；想不靠標註、只用正常影片學「什麼叫正常」；比較看外觀差多少和看下一格預測得準不準兩種算法）：最好 AUROC 0.69；預測式的方法看不到動畫凍結，因為凍住的畫面最好預測。
  • VideoGlitchBench（ACM MM 2026，預印本；想讓模型說出發生什麼、在第幾秒；整理 5,238 支 Reddit 遊戲影片並標時間，提出 GliDe 讓模型分段掃描、推理、定位）：F1 最好約 40%。
  • HASTE（ICSE 2025；想從實況影片自動找出畫面停格；比較相鄰畫面是否幾乎一樣）：precision 89%。
  • 缺口：模型本身不懂時間變化；主要 benchmark TempGlitch 是在一個引擎、兩個範例場景裡注入的。

動作與互動：沒走到，還是沒認出？

  • 兩層難：先在無數操作組合裡走到出錯的路，再判斷「本來應該發生什麼」。
  • 走到
    • 強化學習和好奇心引導：見上面的 Wuji、Bergdahl。
    • GBQA（ICLR 2026 workshop，預印本；想考 LLM 當 QA 工程師；30 款生成的遊戲注入 124 個 bug，agent 最多走 500 步）：最好的模型找到 48%，困難的到 500 步都還沒找完。
  • 認出
    • ACGB（Huynh & Pham，預印本；想知道偵測器要不要知道玩家按了什麼；5 款小遊戲注入 8 種 glitch，同一串操作再跑一次沒 bug 的版本當對照）：只看畫面在「按鍵錯亂」上接近亂猜（0.42–0.53），加上玩家輸入後到 0.87。
  • 缺口：多數研究只報一個 recall，分不出是沒走到還是沒認出；bug 幾乎都是注入的，資料多半沒公開。

資訊與介面：答案不在畫面上

  • 文字被畫壞（重疊、溢出）：看畫面就知道。
    • AG3（ByteDance，FSE 2023；想抓多語系遊戲的文字重疊和溢出；專門訓練一個看截圖的模型）：recall 九成以上；為畫面 glitch 設計的 GLIB 在同一批截圖上幾乎全漏。
  • 內容寫錯（數值沒更新、說明消失）：畫面正常，要知道正確答案。
    • ECHOTEST（IEEE Transactions on Games；想抓字幕跟語音對不上；分別取出字幕文字和語音轉的文字再比對）：本報告找到的研究中，只有字幕這種正確答案剛好在影片裡的情況有自動化方法。
  • 直接問 VLM：VideoGameQA-Bench 的介面題最好只有 40%。
  • 缺口：更新裡最常被修的 Information，正是自動化研究最少的一塊。

四、各類共同的缺口

  • bug 多是研究者自己放的：時間性、互動類的 benchmark 幾乎全是注入的，很少說明真實遊戲裡有多常見。
  • 場景很小又重複：TempGlitch、Sony 穿模、RefGlitch 都用 Godot 範例專案；ACGB 是 64×64 的小遊戲。
  • 公開資料高估表現：82.8% → 46%；AdbGPT 81% → 重測 36%–74%。
  • 正確答案常不在畫面上：當機要步驟、互動要知道按了什麼、資訊要正確數值。
  • 好資料在業界，不公開。
  • 很多關鍵數字還是預印本：如 TempGlitch、ACGB。

五、可以前進的方向

每個方向對應上面一個缺口；細節見可行方向。

方向補哪個缺口BenchmarkBaseline
一、單一遊戲：用注入資料微調 VLM 偵測畫面 bug畫面：公開資料和開發現場的落差部分有
二、互動 bug：agent 自動遊玩，用遊戲內部狀態判斷互動：只看畫面有盲區、分不出沒走到或沒認出部分部分
三、時間性 glitch 的偵測與定位時間性：模型接近隨機有有
四、資訊內容錯誤：畫面顯示值對照遊戲內部值資訊：答案不在畫面上缺缺
五、VLM 在正常畫面上的誤報畫面：模稜兩可的正常畫面有有
六、當機重現：從回報到重現步驟當機：只有 Minecraft 一個 benchmark部分有
七、真實 bug 實證分析共同：注入的 bug 缺少真實頻率的依據不適用不適用
