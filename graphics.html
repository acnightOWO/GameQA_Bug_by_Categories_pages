畫面渲染

一大片洋紅色蓋住地面、整個畫面變成雜訊、角色的手臂穿過牆。這是研究最多的一類，也是自動化做得最好的一類。但「做得好」大多發生在公開的 benchmark 上，換成遊戲公司內部的開發資料，成績就掉了一大截。

示意情境

新版的材質打包流程漏了一張貼圖。在大部分手機上，那片地面變成一大塊不正常的色塊；但在某些 GPU 上，同一個 bug 的色塊顏色又不一樣。網易的 GLIB 團隊（想自動判斷截圖有沒有畫面 glitch，下面會詳細介紹）在真實報告裡就遇過這種情況：同一個 bug，在不同裝置上長得不一樣。

問題怎麼定義

Truelove 等人（想知道哪些 bug 最常被修；一行行標註 Steam 30 款熱門遊戲的更新說明）的定義是「遊戲世界的某個視覺部分被渲染錯誤」。它在 Steam 更新說明裡是第二常見、也是第二常復發的類別；開發者的解釋是畫面的邊角情況太多、測不完，而且畫面對不對本來就有主觀成分。

這類 bug 有一個方便的特性：多數單看一張畫面就能判斷，不需要時間脈絡，也不需要知道玩家做了什麼。所以這一類累積了最多的方法和資料。

現在的做法

流派一 · 監督式學習

自己造出大量壞掉的畫面，訓練分類器

真實的 glitch 截圖很少，這條路線的核心問題是「訓練資料從哪來」。EA SEED 2020 年的做法是在引擎裡直接把貼圖弄壞：拉伸、降解析度、拿掉、換成開發用的暫代貼圖，產生大量樣本訓練 CNN，在正常加四種貼圖錯誤的分類上達到 86.8% 準確率。

網易的 GLIB（FSE 2021）更進一步：直接修改遊戲的渲染程式碼來產生 glitch，例如關掉負責渲染的攝影機、改錯畫面清除的設定。作者也發現，用固定幾種顏色畫假色塊的規則方法會漏掉真實 bug，因為特殊 GPU 上的色塊顏色跟預設的不同。比較不同資料增強方式的結果，可以看出「訓練資料長得像不像真的 bug」決定了一切。這裡用 recall 衡量，也就是真的 glitch 裡抓到多少：

2026 年 10 月的一份預印本把同樣的想法搬到影片上：Rifaat 等人（Ontario Tech；想在同一段畫面裡同時抓出好幾種畫面 bug）在 3 款開源 Unity 遊戲裡裝了 bug 注入器，讓 11 位玩家實際遊玩，隨機注入最多 3 種同時出現的 bug（邊界破洞、貼圖損壞、幾何損壞、深度裁切、深度衝突），切成 77,969 段 2 秒的影片。他們的 ResNet-BiLSTM 在這份資料上 F1 85.78%，勝過一般的 3D 影片分類模型。作者自己也提醒：只有 3 款遊戲、5 種 bug，而且是人工注入的，可能缺少真實 bug 的細節。

流派二 · 只學正常畫面（自編碼器）

不給壞掉的例子，重建不回來的就是異常

監督式學習需要壞掉的樣本；另一條較早的路線乾脆不要。Wilkins 與 Stathis（2022）在自己做的 Unity 平台 World of Bugs 上，只拿正常畫面訓練一個卷積自編碼器：模型學會把正常畫面壓縮再還原，遇到還原不回來的畫面，就判為異常。他們測了十種畫面 bug，結果很兩極：

後續研究的分析指出，這些失敗多半發生在物體背面的幾何沒有被正確渲染、畫面看起來仍然很「正常」的情況。穿模這類細微的錯，在這裡就已經是最難的一類，後面 VLM 也會再撞上它。

流派三 · 直接問 VLM

不訓練，把截圖丟給模型問「哪裡不對」

這一派的共同問題是：模型在公開資料上的分數，換到開發現場還剩多少？2023 年的 GlitchBench（想量 VLM 能不能認出遊戲 glitch）從 Reddit r/GamePhysics 和 Unity 合成場景整理出 593 張 glitch 和 330 張正常畫面，橫跨 205 款遊戲。當時最強的 GPT-4V 平均只有 43.4%，開源模型更低；最難的是動畫和姿勢類的錯誤。兩年後的 VideoGameQA-Bench（想全面測 VLM 能不能做遊戲 QA，出了截圖、影片等多種題型）用 1,000 張 Steam 社群截圖，GPT-4o 在圖片 glitch 偵測上做到 82.8%。看起來問題快解決了。

但同一個研究團隊的 Lu 等人和 EA 合作（論文主題是從 bug 影片找出出事的那一格），在討論段拿一款第一人稱射擊遊戲的內部開發資料重做這個實驗，結果完全不同：

作者的解釋是：公開資料大多是清楚、容易辨認的 glitch，而開發中的 bug 往往很細微。

如果不是挑好的截圖，而是整段測試錄影呢？Lu 等人同樣和 EA 合作，把 41 小時的自動化測試錄影抽成近兩萬張關鍵幀交給模型。gpt-4.1-mini 當偵測器的 precision 是 0.50，也就是報出來的有一半是誤報。在它的結果上再加一個模型當裁判、或用檢索補充上下文，改善都有限：用 gpt-5-mini 當裁判最好，也只到 0.57；圖片檢索則讓結果變差。另外，模型抓到的 bug 裡有 46.8% 是畫面上的錯誤訊息文字。論文把這些算成真的 bug，但它們是最顯眼的一類，不是渲染錯誤。

誤報從哪來？Sony 的研究把範圍縮到單一類型：穿模。他們在 Godot 的第三人稱射擊範例場景中讓 agent 自動探索，再改引擎讓它直接標出哪裡穿模，得到精確的標註。六個模型搭配「明顯正常」的畫面樣本時表現不錯，但正常畫面換成隨機抽樣後，準確率掉了 9 到 15 個百分點：

流派四 · 給一張參考畫面

不問「哪裡不對」，問「跟這張比哪裡不一樣」

人類 QA 在做回歸測試時，會拿上一版確認過的畫面對照。RefGlitch-Bench 在 Godot 場景中做了 1,000 組參考與測試的配對，比較幾種選參考畫面的方式。對多數模型來說，給參考有幫助，而人工挑的參考最好：

可是 VideoGameQA-Bench 裡同樣是「兩張圖比對」的視覺回歸任務，結果非常差。任務是：給同一個場景的參考畫面和測試畫面，加上一段說明哪些變化可以接受（換裝、天氣、光線），判斷要不要放行。在 Unity 場景的部分，錯誤是某個物件被拿掉；另外 70 組來自 YouTube 上過場動畫的 glitch。

流派五 · 用文字找畫面

已經知道 bug 是什麼，找出它出現在影片的哪一格

開發中的 bug 回報常附一段影片，但真正有問題的可能只有其中一格。Lu 等人把一款 FPS 遊戲的 JIRA 回報拿來實驗：先抽出關鍵幀，再讓 GPT-4o 依回報的文字描述挑出最符合的一格。在 247 支影片上，論文定義的 Accuracy@1 是 0.89、F1 是 0.79；換算成影片，有 169 支（68%）的第一個答案是對的。表現好壞跟 bug 類型很有關係：

現在卡在哪裡

  1. 公開資料和開發現場是兩個世界。同樣是 GPT-4o、同樣的提示，公開截圖上 82.8%，在 100 張工業截圖的小實驗裡只有 46%（兩份資料的難度與組成不同）。公開資料偏向清楚、容易辨認的 glitch，而開發中的 bug 通常很細微。
  2. 監督式方法要為每款遊戲準備訓練資料。GLIB 的論文寫明，訓練階段需要遊戲原始碼來產生 glitch；只用真實 bug 截圖訓練時，recall 只有 0.563。
  3. 評估設計可能高估了泛化能力。GLIB 公開的測試集中，192 張 glitch 圖來自 18 款沒參與訓練的遊戲，但 240 張正常圖全部來自參與訓練的那兩款（論文寫的是 365 張正常圖，沒有說明來源）。「沒見過的遊戲的正常畫面會不會被誤判」，這份測試集沒有量到。
  4. 模稜兩可的正常畫面帶來大量誤報。穿模偵測的正常畫面換成隨機抽樣，準確率掉 9 到 15 個百分點；換成靠牆、部分遮蔽這類最模稜兩可的畫面，掉 19 到 25 個百分點。EA 錄影上的 precision 停在 0.50 左右。
  5. 參考畫面本身可能就是壞的。RefGlitch 的實驗中，自動選出的參考有 33.4% 本身就有 glitch，讓正常畫面的誤報率從 0.58 升到 0.84；而即使參考是乾淨的，0.58 的誤報率也已經很高。不相關的參考則讓小模型的 F1 掉到 0.2 以下。
  6. 回歸比對仍然很弱。在需要容忍「允許的變化」的視覺回歸任務上，最好的模型 45.2%，連明顯被拿掉的物件都常常沒發現。
  7. 動畫類一直是最難的。GlitchBench 裡動畫與姿勢類最難；依描述找畫面時，動畫與特效類的 F1 只有 0.51，遠低於光影的 0.94。
  8. 抓得到的偏向最顯眼的那一類。EA 錄影的實驗中，模型抓到的 bug 有近一半是畫面上的錯誤訊息文字；細微的渲染錯誤佔的比例相對少。

可行方向

針對上面的缺口，可以直接開始的方向。資源與參數是估計值；完整的實現方式、需要的參數和文獻依據見可行方向。

單一遊戲：用注入資料微調 VLM

目標輸入一張截圖，輸出有沒有 bug、位置和類別；在這款遊戲的真實 bug 截圖上評估。
做法改遊戲的渲染程式，隨機換貼圖、改顏色、不畫、位移，同時記下被改的位置當標籤；自動遊玩收截圖；用 LoRA 微調開源 VLM。
Benchmark部分：沒有單一遊戲的真實 bug 測試集；可借 GLIB 公開測試集、GlitchBench、VideoGameQA-Bench 做跨遊戲對照。
Baseline有：GLIB、一般影像分類器、只用正常畫面的異常偵測、零樣本 VLM。
主要隱患注入的 bug 跟真實的不像，模型只學會認注入的模式；真實 bug 太細微時連人都分不出來。

VLM 在正常畫面上的誤報

目標量化並降低 VLM 在正常畫面上的誤報，同時不漏掉真的 bug。
做法取模型回答的機率來調門檻；加同場景的參考圖；多問幾次看是否一致；把誤報分類（陰影、遮擋、特殊美術風格、特效）。
Benchmark有：GlitchBench、VideoGameQA-Bench、RefGlitch-Bench。
Baseline有：EA 錄影上 precision 約 0.50，加裁判模型最好 0.57。
主要隱患貢獻偏分析；商用模型更新快，結果容易過時；降誤報通常會犧牲 recall。
