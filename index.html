遊戲 Bug 地圖

遊戲出錯的方式有上百種。這份報告先回到「bug 該怎麼分類」的研究，從資料看哪幾類最常見、最痛，再分頁看每一類目前被做到哪裡、卡在哪裡。

這一頁：
  1. 怎麼替遊戲 bug 分類
  2. 哪些最常見、最嚴重
  3. 為什麼這些 bug 難抓
  4. 五個需要攻克的主題
  5. 五個主題的共同處境

一、怎麼替遊戲 bug 分類

2010 年，Lewis、Whitehead 與 Wardrip-Fruin 想回答一個看似簡單的問題：遊戲到底會「怎麼」壞掉？他們沒有去讀程式碼，而是蒐集線上影片、文章和玩家社群裡的 glitch，用玩家看到的樣子來分類。這個選擇很關鍵：同一個畫面上的錯，背後的原因可能有十種，但玩家只會感受到一種。

他們的分類最上層只切一刀：跟時間有關的和跟時間無關的。前者要看前後變化才知道不對，例如事件該發生卻沒發生、進行中的動作被莫名中斷；後者一張畫面就看得出來，例如物件出現在不該在的位置、畫面渲染錯誤。這套分類一共 11 種類型。

十一年後，Truelove、de Almeida 與 Ahmed 把這套分類拿去對照真實世界。他們讀了 Steam 上最熱門的 30 款遊戲、723 次更新的更新說明，一行一行標記，總共 12,122 筆 bug 修正。Lewis 的 11 類不夠用，他們又補了 9 類（音效、鏡頭、碰撞、當機、使用者介面、物件持續性、事件觸發、物件屬性交互、作弊漏洞），變成 20 類。

之後還有更大的整理。Butt 等人做了多來源文獻回顧，把分類擴充到 63 類、第一層 8 大類，並用業界從業者問卷驗證；它的期刊版本 VGBT 回顧了 436 份來源，並套用到開源遊戲 0 A.D. 的 594 份 bug 回報上。不過這兩套分類沒有提供大規模的頻率資料，所以這份報告仍以 Truelove 的 20 類為骨架。

二、哪些最常見、最嚴重

分類只告訴我們有哪些種類，要知道哪些最該優先處理，得看實際的修正紀錄。Truelove 的資料給了一個清楚的排名：

指標前三名最後三名
最常出現在更新裡Information（資訊沒有正確傳達給玩家）、Game Graphics（畫面渲染錯誤）、Action（做不到該做得到的動作，或反過來）Camera、Interrupted Event、Exploit
最常反覆復發Crash、Game Graphics、Triggered Event（A 該觸發 B 卻沒觸發）Camera、Event Occurrence、Interrupted Event（這三類沒有任何復發紀錄）
最嚴重（出現在緊急更新的比例）Crash（38%），其次是 Object Persistence、Triggered Event—

作者在討論中特別點名：Information bug 雖然最常見，但復發率和嚴重度都不高；當機不是最多的，卻是復發最多、最嚴重的一類，「研究者或許應該把更多力氣放在當機上」。

Steam 的更新說明是 PC 遊戲的視角。手機遊戲的相容性測試給了另一個視角：測試公司 TestBird 在 2020 年測了 11,476 款手機遊戲，共 552,851 個相容性問題；騰訊 WeTest 也有自己的統計。兩份資料都由網易的 GLIB 論文轉引。

三、為什麼這些 bug 難抓

Politowski 等人回顧遊戲測試的文獻時發現，開發者「幾乎完全依賴人工試玩和測試者的經驗」。他們另一份開發者問卷顯示，大家對自動化 agent 普遍存疑，最常見的顧慮是前期要投入的成本：建工具、訓練 agent，而且小型團隊根本找不到適用的方案（這份問卷只有 12 位受訪者）。

自動化之所以難推，跟 bug 本身的性質有關。Truelove 除了標記更新說明，也問卷調查了 47 位遊戲開發者，請他們說明這些 bug 為什麼一直出現：

開發的重心是遊戲機制，資訊相關的元件通常被排到流程最後，截止日一到就做不好。關於 Information bug
正確的資訊可能「埋在資料檔裡」，測試的人不一定找得到。關於 Information bug（作者整理開發者的回答）
畫面的邊角情況很容易在測試時漏掉。關於 Game Graphics bug
每一種動作在每一種情境下的每一種順序，組合起來通常根本不可能測完。關於 Action bug

這四句話指出四種困難：資訊被排到最後才做、正確答案不在畫面上、畫面的邊角情況太多、動作組合多到走不完。後面五頁會一再碰到這幾件事。

四、五個需要攻克的主題

這份報告把 bug 分成五個主題，各開一頁。挑選的理由各不相同：當機最嚴重；畫面渲染和資訊類最常見；動作與互動常見又最難測；時間性 glitch 在更新說明裡很少，但它是 Lewis 分類最上層的一半，也是近兩年研究最集中、成績最差的地方，它少見也可能只是因為難以被發現和寫進更新說明。每一頁都依同樣的順序講：問題怎麼定義、現在有哪幾種做法、各自做到哪裡、還卡在哪裡。

當機
對應 Truelove：Crash
最嚴重、最常復發。難的不是「認出當機」，而是從玩家一段模糊的回報，重新走到當機的那一刻。
畫面渲染
對應 Truelove：Game Graphics，以及看得見的 Collision、Position of Object
量最大、研究最多。公開 benchmark 上表現不錯，換到真實的開發資料就大幅退步。
時間性 glitch
對應 Lewis 的 temporal 類中，跟動作與畫面變化有關的部分
單張畫面看不出來，要看前後變化。現有的影片模型在這裡幾乎是用猜的。
動作與互動
對應 Truelove：Action、Triggered Event、Context State、Object Persistence
組合多到測不完，而且很多問題只看畫面分不出來，要知道玩家按了什麼。
資訊與介面
對應 Truelove：Information、User Interface
更新說明裡最常被修的一類。文字被畫壞還看得出來；內容寫錯了，得知道正確答案才看得出來。

不在這份報告範圍內的類別：音效、網路與效能（Implementation Response；卡頓除外，它的偵測方式跟時間性 glitch 相同，放在時間性那一頁）、作弊漏洞、NPC 行為、鏡頭、數值設定（Value）、物件屬性交互、出界（Bounds）。它們同樣重要，但研究脈絡跟上面五類差很多。

五、五個主題的共同處境

把五頁放在一起看，有幾件事反覆出現。這裡只描述現況。

  • 評測用的 bug 大多是研究者自己放進去的。時間性、互動類的 benchmark 幾乎全是注入的；類別和難度由作者決定，很少說明在真實遊戲裡有多常見。
  • 同一批小場景被反覆使用。TempGlitch、Sony 的穿模研究、RefGlitch-Bench 都建在 Godot 的範例專案上；ACGB 是 64×64 的小遊戲。
  • 公開資料普遍高估了表現。同樣的模型和提問方式，公開截圖上 82.8%，工業開發資料上 46%；AdbGPT 自報 81%，重測 36% 到 74%。
  • 「本來應該發生什麼」常常不在畫面上。當機要從回報推回步驟，互動 bug 要知道玩家按了什麼，資訊類要知道正確數值；只看畫面的方法在這三處都碰到原理上的限制。
  • 最好的資料在業界，而且是封閉的。工業 QA 錄影、bug 單和多語系截圖出現在論文裡，但幾乎都沒有公開。
  • 不少關鍵結果還是預印本。TempGlitch、ACGB 等近一年的重要數字，尚未經過正式審查。
