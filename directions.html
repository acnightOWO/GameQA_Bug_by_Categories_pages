方向一

單一遊戲：用 mutation 資料微調 VLM 偵測視覺 bug

目標輸入一張截圖，輸出有沒有 bug、bbox、類別；在這款遊戲的真實 bug 截圖上評估。
實現方式改遊戲的渲染程式，在繪製時隨機替換貼圖、改顏色、不畫、位移、截斷字串，同時記下被改元素的 bbox 當標籤。用腳本或 AI 自動遊玩收截圖。以 LoRA 微調開源 VLM（如 Qwen-VL），輸出 JSON。
需要的可修改渲染層的開源遊戲；可 headless 執行。訓練資料約 1 萬到 5 萬張（正常與有 bug 約各半）。8B 模型 LoRA（r 16–64）約需 1 張 48GB 或 2 張 24GB GPU；32B 需 QLoRA 或多卡。真實測試集約數百張，需人工標 bbox。
Benchmark部分　沒有單一遊戲的真實 bug 測試集。可借用 GLIB 公開測試集、GlitchBench、VideoGameQA-Bench 做跨遊戲對照。
Baseline有　GLIB（CNN）、ResNet／ViT 分類器、PatchCore 等只用正常畫面的 anomaly detection、零樣本 VLM（GPT-4o、Qwen-VL）。
文獻的啟示
  • GLIB 只用真實 bug 截圖訓練時 recall 只有 0.563，論文也寫明產生訓練資料需要遊戲原始碼：注入資料有必要，但每款遊戲都要自己做。
  • 網易 201 張 glitch 截圖裡 56% 是不正常的色塊，文字類只佔 2%：注入類型應該依真實分布挑，不是想得到什麼就做什麼。
  • World of Bugs 的自編碼器對黑畫面、貼圖遺失幾乎全抓得到，對穿模幾乎抓不到：明顯的 bug 簡單方法就夠，真正難的是細微的。
  • GPT-4o 在公開截圖上 82.8%，在工業開發截圖上 46%：公開資料偏向明顯的 glitch，評估要用真實開發中的 bug。
  • GLIB 公開測試集的正常圖全部來自訓練用的遊戲：測試集要放沒見過的畫面的正常圖，才量得到誤報。
可能的隱患
  • 注入的 bug 和真實 bug 長得不一樣，模型只學會認注入的模式。
  • 很多注入的結果肉眼看不出來（被蓋住、顏色差太少），標籤會有雜訊，要做可見性過濾。
  • 真實 bug 太細微時，人都分不出來，評估沒有意義（fheroes2 就是這個情況）。
  • 真實截圖的解析度、視窗邊框、壓縮跟訓練資料不同，要做資料擴增。
  • 跟 GLIB 差別不大，創新點容易被質疑。

候選遊戲（開源、3D、回報常附遊戲畫面；回報數量還沒實際統計）

遊戲類型 / 技術回報裡的 bug 例子注意
OpenMW開放世界 RPG，C++ / OpenSceneGraph，GitLab地形貼圖透明、角色臉全黑、UI 貼圖壞掉需要 Morrowind 原版素材（付費）
0 A.D.即時戰略，C++，Gitea單位只剩武器可見、建築顏色錯、地形閃爍素材免費；VGBT 已用它的 594 份回報做分類
Daggerfall UnityRPG，Unity，GitHub房屋貼圖錯、地面出現格線原版素材官方免費；可接 Unity 工具
Veloren體素 RPG，Rust / wgpu，GitLab還沒找到具體例子素材免費
SuperTuxKart賽車，C++，GitHub殘影、陰影閃爍很多是 Intel / Mesa 驅動問題

前三款不在 GitHub，所以不在 OSSGameBench。3D 遊戲的畫面回報常有一部分是 GPU 驅動造成的，測試集要先剔除。

方向二

互動 bug：agent 自動遊玩，用遊戲內部狀態判斷

目標找出按了沒反應、點不到、任務無法完成、卡住等 bug；分開報告「沒走到」和「走到但沒偵測到」。
實現方式agent（RL 或 LLM / VLM）只用鍵盤滑鼠操作。判斷用遊戲內部資料：輸入後狀態有沒有變、UI 是否擋住點擊、任務旗標。可記錄成功通關的操作序列，在新版本重播比對。
需要的能讀內部狀態的遊戲（開源或引擎外掛）；可重現的隨機種子；大量平行執行的 CPU。LLM agent 每局會呼叫模型數百到數千次，API 成本或本地推論 GPU 要估。
Benchmark部分　GBGallery（5 款遊戲、76 個真實 bug，只有執行檔）；GBQA、ACGB 未公開；World of Bugs 停止維護。
Baseline部分　隨機、DQN、A2C、好奇心 A2C、Wuji（GBGallery 內建）；TITAN（未公開）。
文獻的啟示
  • ACGB 裡隨機策略觸發的 bug 有 0.718 被認出來，沒找到的大多是根本沒走到：瓶頸在探索，不在辨識。
  • 以「驚訝」為目標的 agent 觸發 bug 的比例（0.275）比亂按（0.435）還低，誤報多了近 15 倍：好奇心式探索會把 agent 帶偏。
  • 只看畫面的方法在按鍵錯亂上接近或低於隨機（VideoMAE 0.42、V-JEPA 2 0.52）：這類 bug 一定要知道玩家按了什麼。
  • GBQA 的困難 bug 到 500 步還沒飽和；開發者也說所有動作順序在組合上測不完。
  • TITAN 的 LLM agent 抓到的注入 bug 約是 RL 的兩倍，已部署在 8 條實際 QA 流程；但開發者問卷顯示，大家對自動化 agent 最大的顧慮是前期成本。
可能的隱患
  • bug 由自己放、自己評估，會被質疑循環論證。
  • 操作組合太多，困難的 bug 要很長的序列才走得到，結果主要被探索能力決定。
  • 讀得到內部狀態時，很多 bug 用規則就判斷完了，VLM 的角色不明確。
  • 每款遊戲都要寫操作介面和狀態讀取，工程量大，很難換遊戲。
方向三

時間性 glitch：影片偵測與定位

目標輸入一段遊戲影片，判斷有沒有閃爍、動畫凍結、跳幀、瞬移，並給出時間點。
實現方式(1) 只用正常影片訓練，用特徵距離或預測誤差當異常分數（VideoMAE、V-JEPA）。(2) 在遊戲裡注入時間性 bug，產生有時間標籤的影片微調影片 VLM。(3) 直接從引擎記錄每幀狀態，用規則判斷。
需要的影片片段約 2–10 秒，取樣 4–16 fps。影片 VLM 的輸入 token 很多，微調 8B 模型建議 80GB GPU 或多卡。注入資料需要可控制的遊戲環境。
Benchmark有　TempGlitch（750 組有 / 無 bug 配對）、VideoGlitchBench（120 款遊戲、5,238 支影片）、PhysGame（880 支）。
Baseline有　VLM 在 TempGlitch 上 49–54%；VideoMAE kNN AUROC 0.69；VideoGlitchBench 最佳 F1 約 40%（閉源模型直接問 26%）。
文獻的啟示
  • 凍結的畫面最容易預測，所以用預測誤差的方法在「動畫凍結」上反而低於隨機；外觀距離和可預測性在不同類別各有盲點，可以互補。
  • 作者把特徵的有效秩從 1.13 拉到 21.30，偵測成績幾乎沒動：問題不在特徵塌縮。
  • 通用影片的 TimeBlind，最強模型 48.2%、人類 98.2%；MotionBlind 發現多給畫面或挑更好的畫面都補不上差距：不是取樣不夠，是模型本身不懂時間變化。
  • GELID 用實況主的字幕切出問題片段，切片段和分群做得不錯，但判斷問題類別的效果有限。
  • 時間性 bug 在 Steam 更新說明裡很少，但可能只是因為難以被發現和寫進更新說明。
可能的隱患
  • 主要 benchmark 都還是預印本，數字可能改變，也可能很快有人做出更好的方法。
  • 取樣 fps 太低會漏掉閃爍這類只持續幾幀的 bug；太高則運算量暴增。
  • 凍結的畫面最好預測，用預測誤差的方法會反而判成正常。
  • 注入的影片多是簡單場景，跟真實遊戲影片差距大。
方向四

資訊內容錯誤：畫面顯示值 vs 遊戲內部值

目標找出數值沒更新、顯示錯誤、說明消失、名稱不一致。
實現方式OCR 或 VLM 讀出畫面上的文字和數字，跟遊戲內部的值或資料檔比對。拿不到內部值時，比對同一數值在不同畫面、不同時間是否一致。
需要的能匯出畫面上每段文字及對應內部值的遊戲 hook；遊戲字型的 OCR 準確度要先測。
Benchmark缺　沒有公開資料集；只有零星的真實回報（fheroes2 #7002、TRX #2659、vcmi #3412）。
Baseline缺　AG3、OwlEye 只處理文字重疊、溢出，不處理內容錯。只能自建 OCR + 規則、零樣本 VLM 當 baseline。
文獻的啟示
  • Information 是 Truelove 12,122 筆修正裡最常見的類別，但復發率和嚴重度都不高。
  • 開發者說正確資訊常常「埋在資料檔裡」，資訊相關元件又常被排到開發最後：答案不在畫面上，這是只看畫面的方法在原理上的限制。
  • GLIB 在 AG3 的真實截圖上，文字重疊 recall 7%、文字溢出不到 1%；專門的 AG3 都在 90% 以上，部署兩年找到超過 2,000 個問題：通用偵測器不行，專門做的有效，而且有業界需求。
  • ECHOTEST 比對字幕和語音，真實遊戲上 precision 98%：當「另一個正確來源」剛好在影片裡時，內容錯誤是可以自動抓的。
  • 美術字和做成圖片的文字會讓 OCR 失效；VideoGameQA-Bench 的 UI 單元測試最好也只有 40%。
可能的隱患
  • 能讀內部值時直接比對就好，不需要 VLM，研究價值會被質疑；要找拿不到內部值的情境（黑箱、錄影）。
  • 遊戲的美術字、圖片文字 OCR 讀不出來。
  • 很多正確值是計算出來的，「什麼才是對的值」本身要定義。
  • Benchmark 和 baseline 都自己做，說服力較弱。
方向五

VLM 誤報：在真實正常畫面上的 false positive

目標量化並降低 VLM 在正常畫面上的誤報，同時維持 recall。
實現方式取 VLM 回答 true / false 的機率做 threshold 校準；加同場景的參考圖；多次取樣看一致性；把誤報分類（陰影、遮擋、特殊美術風格、特效）。
需要的大量隨機抽樣的正常畫面（自動遊玩錄製即可，數千張）；能取得 logprob 的模型（開源或支援 logprobs 的 API）；主要是推論成本。
Benchmark有　GlitchBench、VideoGameQA-Bench、RefGlitch-Bench。
Baseline有　EA 錄影上 precision 約 0.50，加 judge 模型最好 0.57；穿模偵測換成隨機正常畫面後掉 9–15 個百分點。
文獻的啟示
  • EA 41 小時測試錄影上，gpt-4.1-mini 的 precision 0.50；加 judge 模型最好到 0.57，圖片檢索反而讓結果變差：事後過濾的改善有限。
  • 模型抓到的 bug 有 46.8% 是畫面上的錯誤訊息文字：模型偏向最顯眼的東西，細微的渲染錯誤反而少。
  • Sony 的穿模研究中，正常畫面換成隨機抽樣後準確率掉 9–15 個百分點，換成靠牆、部分遮蔽這類模稜兩可的畫面掉 19–25 個百分點：誤報主要來自模稜兩可的正常畫面。
  • RefGlitch：給參考圖對多數模型有幫助，人工挑的最好，但 Gemini 反而變差；不相關的參考讓小模型 F1 掉到 0.2 以下。
  • VideoGameQA-Bench 的視覺回歸（參考圖 vs 測試圖）最好的模型只有 45.2%，連明顯被拿掉的物件都常常沒發現。
可能的隱患
  • 貢獻偏分析，較適合 workshop 或短文。
  • 商用模型更新快，結果容易過時。
  • 降低誤報通常會犧牲 recall，要報完整的 precision–recall 曲線。
  • 參考圖本身可能有 bug（RefGlitch 自動選的參考有 33.4% 有問題）。
方向六

當機重現：從 bug report 到重現步驟

目標輸入玩家的當機回報，自動在遊戲裡重現當機。
實現方式LLM 把回報整理成步驟，再由 agent 在遊戲裡執行；用 stack trace 縮小範圍。比較遊戲專用指令集和通用 computer-use agent。
需要的能切到出事版本的遊戲（可編譯舊版）；每份回報要人工確認能重現；遊戲的操作 API。
Benchmark部分　BugCraft-Bench（Minecraft，86 份）是唯一遊戲版本。
Baseline有　BugCraft；通用 computer-use agent 最好 25.5%，UI-TARS 0%。
文獻的啟示
  • 當機在 Truelove 的資料裡出現在緊急更新的比例最高（38%），也最常復發：需求很明確。
  • AdbGPT 自報重現率 81.3%，兩份他人重測是 74% 和約 36%：要用別人沒調過的資料評估。
  • BugCraft 中 LLM 整理出的步驟約三分之一缺步驟、下錯指令或邏輯不通：瓶頸常在讀懂回報。
  • BugCraft 的作者指出，Android 的方法把畫面轉成文字處理，但遊戲需要空間推理和狀態相依，app 的方法搬不過來。
  • Ubisoft 的當機分流研究，最好的方法找出超過一半的病毒式當機類型：上線後的分流也是一個可做的子問題。
可能的隱患
  • 回報常缺步驟，BugCraft 的 100 份裡 14 份人都重現不了。
  • 舊版本編譯、存檔、設定還原的成本很高。
  • 跟視覺、VLM 的關係較遠。
方向七

真實 bug 實證分析

目標統計真實遊戲 bug 中，多少看單張截圖就能判斷、多少要看影片、多少要知道玩家輸入或遊戲狀態。
實現方式從開源遊戲的 issue 抽樣，按 Lewis / Truelove 分類，再標「判斷需要什麼資訊」；兩人獨立標註，計算 Cohen's kappa。
需要的樣本約 300–500 則（依類別分層抽樣）；兩位標註者；標註指南。
Benchmark不適用。資料來源：OSSGameBench（950 個 GitHub repo、約 32 萬則 issue），可另加 OpenMW、0 A.D. 等。
Baseline不適用；可對照 Truelove 的統計和 VGBT 在 0 A.D. 上的分類。
文獻的啟示
  • Lewis 的 11 類、Truelove 的 20 類、Butt 的 63 類都說明「有哪些類」，但除了 Truelove，都沒有大規模的頻率資料。
  • 現有時間性、互動類 benchmark 的 bug 幾乎都是作者注入的，類別和難度由作者決定，很少說明在真實遊戲裡有多常見：實證結果正好能補這個依據。
  • OSSGameBench 只有各專案自訂的 label，沒有 bug 分類，也沒有可編譯版本或重現步驟；一般軟體有 Defects4J，遊戲沒有。
  • VGBT 已把分類套用到 0 A.D. 的 594 份回報，可以當標註方式的參考。
  • 手機遊戲相容性測試裡，畫面顯示異常佔約 40–48%、當機約 29%（TestBird、WeTest）：PC 更新說明和手機測試看到的分布不同，平台要分開看。
可能的隱患
  • 開源遊戲的 bug 分布可能跟商業遊戲不同。
  • issue 描述不完整，很多只看文字判斷不了類別。
  • 屬於實證研究，沒有方法貢獻，適合 MSR 類短文。
